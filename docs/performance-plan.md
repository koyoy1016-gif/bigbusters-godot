# 重さの改善策（2026-10-19・版51）

## 結論（先に）
- **ゲームのなめらかさは、公開先（URLの容量・回線）では変わらない。** 遊んでいる間の重さは、スマホの中の計算と描画で決まる。公開先が影響するのは「最初の読み込みの待ち時間」だけ。
- かくかくの主な原因は、**描く回数が多すぎた**ことと、**iPhone の画面の画素数のまま3Dを描いていた**こと。版50・51で直した。
- まだ実機（iPhone）の数字が取れていない。URL の末尾に `?perf=1` を付けると、画面の左上に数字が出る。その数字で次の手を決める。

## 測った数字（この環境・AI3人つきの戦い）
| | 版49 | 版50 | 版51 |
|---|---|---|---|
| 1コマの描画の回数（画質 低） | 278 | 78 | 80 |
| 1コマの描画の回数（画質 高） | 1295 | 166 | 152 |
| 描く部品の数 | 251 | 27 | 27前後 |
| ボス1体を描く面の数 | 154 | 19 | 23（形はずっと細かい） |
| 3Dを描く画素（iPhone 16 Plus くらいの画面） | 約360万 | 約360万 | 低 約45万／高 約90万 |
| FPSの上限（画質 低） | 30 | 30 | なし（画面の更新に合わせる） |

参考：以前の iPhone の実測で、描画の回数が221回のとき FPS 39、12回のとき FPS 59 だった。

## 原因と、やったこと
1. **部品を1個ずつ描いていた**（ボス154・主人公87）→ 動きが同じ部品を1つの形にまとめた（`scripts/core/mesh_merge.gd`）。ボスの腕・しっぽは MultiMesh（まとめて1回で描く）。主人公の装備は骨についていく1つの形に。
2. **画質「高」の影を4段に分けて描いていた**→ 1段に。影の画像も小さく（高 2048）。
3. **ボスの腕の形を毎コマ作り直していた**→ 形は作り直さず、向きと大きさだけ変える。
4. **iPhone の画面の画素数（約360万）のまま3Dを描いていた**→ 画質ごとに「3Dの画素数の目安」を決め、自動で細かさを決める（`Quality.scale_for`。数値は `data/quality.json` の `target_3d_pixels`）。文字やボタンはくっきりのまま。
5. **FPSの上限30**（画質 低）→ やめた。ブラウザでは、30に制限すると間隔がそろわず、かくかくして見える。
6. **白い点滅で、材質の種類を切り替えていた**（初めて光るたびに、ブラウザで描き方の作り直しが起きて一瞬止まる）→ 明るさだけ変える。

## 次の手（実機の数字を見て選ぶ）
`?perf=1` の表示：`FPS`（1秒の平均）、`さいだい`（いちばん長かった1コマ。引っかかり）、`びょうが`（描画の回数）、`3D`（3Dを描いている画素の大きさ）。

| 実機の数字 | 考えられる原因 | 次の手 |
|---|---|---|
| FPS が 55〜60 | 問題なし | このまま。キャラ・ステージを増やすたびに測る |
| FPS が低く、画質「低」にすると上がる | 画素を描く重さ（GPU） | ① `target_3d_pixels` をさらに下げる ② 画質「低」では、段のある陰影・縁の光・質感の模様を切る（材質を軽く） |
| FPS が低く、画質を変えても同じ | 計算の重さ（CPU） | ① 主人公の骨（137本）・面（約3万）を減らす（味方3人が本物のモデルになると4倍になる）② 遠くのキャラの動きの更新を間引く ③ スクリプトの毎コマの処理を減らす |
| ふだんは速いが、ときどき止まる（さいだい が大きい） | 初めて出る物の描き方の作り直し | 読み込み中に、全部の材質を一度描いておく（あたため） |

## 読み込みの待ち時間（公開先の話）
- いまの書き出し：`index.wasm` 約39.5MB（圧縮すると約10MB）＋データ約2MB。
- 小さくする方法：使っていないエンジンの機能を外した「自前の書き出しテンプレート」を作る（未着手。半分くらいになる見込み。**未確認**）。

### 公開先の比較（2026-10-19 に公式の説明で確認）
| 公開先 | 料金 | 容量・転送の上限 | このゲームでの注意 |
|---|---|---|---|
| GitHub Pages（いま） | 無料 | サイト全体 1GB まで。転送は月 100GB が目安（ゆるい上限） | 1回の読み込みが約40MB なら、月に約2,500回が目安（キャッシュが効けば、もっと多い）。友達20人なら十分 |

- 収益化用（アプリ2、1000人が目標）は、GitHub Pages の規約・転送量の両方の点で、別の公開先が必要になる見込み。そのときに最新の条件を確認して決める。

## Three.js のゲームとの違い
- 前のゲーム（Three.js）は、ブラウザの JavaScript で直接動く。Godot のブラウザ版は、エンジン全体（wasm）をブラウザの中で動かすので、同じ見た目でも、もとの負担が大きい。
- それでも、4人＋ボス1体の規模なら、描く回数と画素数を抑えれば 60FPS は狙える（版51の対策は、そのため）。
- 実機の数字を見ても足りない場合に限り、「ブラウザ版だけ別の作り方にする」などの大きな判断をする（いまは不要）。
